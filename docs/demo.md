# Демо за 3–5 минут

1. Соберите Release и запустите backend на 5071 и шлюз на 5070 по [README](../README.md).
2. Выполните запрос из README и откройте `/metrics`. После одиночного успешного POST счётчик `accepted` у `normal /work` вырастет на один, а `inFlight` вернётся к нулю.
3. В третьем терминале запустите нагрузку.

```sh
dotnet run --project tools/Load -c Release --no-build -- http://127.0.0.1:5070 12
```

4. Остановите только шлюз и повторите запуск нагрузки после каждого из двух запусков шлюза ниже. Останавливайте шлюз перед сменой режима, чтобы очистить метрики и квоты.

```sh
dotnet run --project src/RequestLimiter -c Release --no-build -- --Gate:Mode=off
dotnet run --project src/RequestLimiter -c Release --no-build -- --Gate:Mode=standard
```

По умолчанию генератор отправляет запросы на `/work?delayMs=80` каждые 125 мс для обычного клиента и каждые 10 мс для агрессивного. Отправка не ждёт предыдущего ответа. Таймер может пропускать тики, поэтому смотрите фактическое число `sent`. Один прогревочный запрос не входит в отчёт. Процентили считаются отдельно для всех ответов и для успешных ответов. Для `/bulk` интервалы составляют 320 и 25 мс соответственно. Четвёртый аргумент сохраняет CSV с кодом и задержкой каждого запроса.

```sh
dotnet run --project tools/Load -c Release --no-build -- http://127.0.0.1:5070 12 /bulk bulk-samples.csv
```

В режиме `off` оба потока могут ждать общий backend и получать `504`. В двух других режимах агрессивный клиент в основном получает `429`, иногда `503`. Сравните успешные ответы и p95 у `normal`. Точные значения зависят от среды.
