# Проверка

Повторная проверка 8 ноября 2026 года. Windows 11 Pro (22631), Intel Core i7-8750H, 12 логических процессоров, 31,8 ГиБ RAM. SDK 10.0.403, ASP.NET Core и .NET Runtime 10.0.14. Backend, шлюз и клиент нагрузки работали на одной машине по loopback.

| Команда | Результат |
| --- | --- |
| `dotnet restore` | Восстановлены зависимости четырёх проектов |
| `dotnet build -c Release --no-restore` | 0 предупреждений, 0 ошибок |
| `dotnet test -c Release --no-build` | 17 пройдено, 0 пропущено |
| `dotnet format --verify-no-changes --no-restore` | Код возврата 0 |

Команды выполнялись через `.\.dotnet\dotnet.exe`. Прогона на GitHub Actions и Linux не было.

Добавлены проверки исчерпания и пополнения стандартной корзины, очистки без сброса квоты, HTTP 429 с `Retry-After` и раздельных квот. Проверки очереди и разрыва соединения запускаются в обоих режимах. Отдельные HTTP-тесты проверяют зависание после заголовков backend, слишком большой ответ и незавершённую загрузку. После каждого из этих сбоев тест одновременно занимает оба слота следующими запросами.

## Нагрузка

Из каталога `FairGate` соберите Release и запустите backend в первом терминале:

```sh
dotnet build -c Release
dotnet src/Backend/bin/Release/net10.0/Backend.dll --Logging:LogLevel:Default=Warning
```

Во втором терминале запускайте шлюз с `off`, `custom` или `standard`, перезапуская его перед каждым прогоном:

```sh
dotnet src/RequestLimiter/bin/Release/net10.0/RequestLimiter.dll --Gate:Mode=off --Logging:LogLevel:Default=Warning
```

В третьем терминале запускайте клиент. Сделайте по три прогона на каждый режим и маршрут, указывая отдельное имя CSV.

```sh
dotnet tools/Load/bin/Release/net10.0/Load.dll http://127.0.0.1:5070 6 /work work-off-1.csv
dotnet tools/Load/bin/Release/net10.0/Load.dll http://127.0.0.1:5070 6 /bulk bulk-off-1.csv
```

Каждый прогон длился 6 секунд плюс завершение запросов. Backend имел четыре общих слота и задержку 80 мс. Интервалы обычного и агрессивного клиентов составили 125/10 мс на `/work` и 320/25 мс на `/bulk`. Запросы прогрева исключены. [Архив серии](measurements/review-load.zip) содержит 18 CSV с кодами и задержками запросов и 18 текстовых сводок с числом отправок и разбивкой по статусам.

На `/work` обычный клиент получил 15 успешных ответов из 144 без лимитов и 144 из 144 в каждом режиме с лимитами. Без лимитов все отказы обоих клиентов были `504`. С лимитами у агрессивного клиента преобладали `429`, и по девять запросов за три прогона получили `503` в каждом режиме.

На `/bulk` выбранная частота укладывалась в общую ёмкость симулятора. Без лимитов оба клиента завершили все запросы. С лимитами агрессивный клиент получил 645 ответов `429` из 720 в каждом режиме, обычный завершил все 57 запросов. Короткие прогоны с 19 запросами обычного клиента на `/bulk` дают мало данных для оценки хвоста задержек. По этой серии нельзя определить предельную ёмкость или устойчивое преимущество одного алгоритма.
